4 · Methodology, formulas and honesty limits

Model v1.0.0 · deterministic

Fit score (0–100)

fit = 0.32·requirement + 0.14·level + 0.16·evidence + 0.10·access + 0.12·comp + 0.16·feasibility

  • Requirement overlap. Each must-have requirement is worth 1.0 and each nice-to-have 0.35. A requirement counts as met when any profile token (skills + target-title words, lowercased, split on non-alphanumerics, 3+ characters) appears inside the requirement text or the requirement text appears inside the token. Score = met weight ÷ total weight.
  • Level. Full credit inside the archetype's expected years band; outside, max(0, 1 − distance/6).
  • Evidence. Number of the five artifacts you ticked, divided by 5, capped at 1.
  • Access. 0.6·(network/100) + 0.4·(1.0 warm channel named, else 0.35); internal, alumni and referral count as warm channels.
  • Comp. Full credit when your floor is at or below the band maximum. Above it, max(0, 1 − (floor − bandMax)/(0.35·bandMax)). Below 80% of the band minimum, comp credit is set to 0.85 to flag under-levelling risk because the role would likely under-pay you.
  • Feasibility. 0.5·location + 0.3·remote + 0.2·schedule, each taken from the explicit selects (0 / 0.35 / 0.7 / 1).

Probability heuristics (not predictions)

interview% = clamp(baseInterview · (0.40 + 1.70·fit1.15) · competitionFactor, 1, 92)

competitionFactor = clamp(1 + 0.9·(0.5 − competition), 0.45, 1.55)

offer% = clamp(interview% · (baseOffer/100) · (0.55 + 0.95·evidence) · (1 − 0.45·credentialGate), 0.5, 85)

priority = 0.65·fit + 0.25·(1 − competition) + 0.10·evidence

  • The reported band is −35% / +35% relative to the point estimate, for example 18% (band 12–25%).
  • Base interview rate defaults to 12% of applications and offer-given-interview to 18%; both are editable assumptions in panel 2.
  • Archetype competition, velocity weeks, remote feasibility and credential gate are editorial estimates for the archetype, not measured applicant counts. Treat them as conversation starters.
  • Comp bands are annual base salary in $ thousands, indicative for the sector and level. They vary by institution, union, geography and budget year — verify locally.
  • Identical profile inputs always produce an identical order; ties break by role id ascending. No network calls, no tracking, no AI inference runs here.

PROJECT GOVERNANCE · ADMISSIBILITY GATE

Project Admissibility Protocol

Five layers, one verdict, and a rule that applies to any project and any priority list. Read the exhibit, then run the same tests against a real proposal: a good idea still has to survive the measurement, alignment and provenance layers before it may be called admissible.

EXHIBIT + RUNNABLE GATE Offline · nothing leaves this browser 7 SMARTER fields · 6 alignment rows · 4 provenance labels · 5 disqualifiers

The exhibit below is the canonical protocol. The styled cards restate it for reading and printing; the ASCII block at the end is the source text to copy into a governance pack. Both say the same thing: every layer is a test, not a formality.

Read the order. A project moves from the measurement contract, to mission alignment, to provenance, to onboarding, to the prohibitions. A failure in Layers 1–3 or 5 is a blocking finding; Layer 4 gaps become documented conditions. The priority list never overrides a failed test.
LAYER 1

SMARTER — the measurement contract

All seven fields blocking
S · SPECIFY
one named deliverable, one owner
M · MEASURE
one existing metric + baseline date
A · ATTAIN
named capacity, confirmed by a unit lead
R · RELEVANCE
link to a NAMED priority (not the mission)
T · TIMEBOX
dated finish + governance checkpoint
E · EVALUATE
cadence + on/warn/off thresholds
R · REVIEW
adopt / rework / stop + named decider

Fails if: any field is a verb, an assumption, or a name without a role behind it.

LAYER 2

MISSION ALIGNMENT — the admissibility test

ANCHOR · MAP · STEWARD block
ANCHOR
which named priority does this advance?
MAP
which function owns delivery, which support?
PARTNER
which offices must be consulted first?
CONSENT
who agrees, who is informed?
HANDOFF
what is handed to whom at the end?
STEWARD
which system of record owns the data?

The generic test:

  • ANCHOR names a real priority.
  • MAP names a real owner.
  • STEWARD names a real system.

If any of the three is empty, the project is not admissible — however good the idea is.

LAYER 3

PROVENANCE — the truth contract

One label per figure

Every published figure carries exactly one label:

  • PUBLISHEDcitable public source
  • SYSTEM OF RECORDowned system extract, dated
  • PLANNING ESTIMATEassumption stated alongside
  • SAMPLEsynthetic, layout only, never reported

Rule: SAMPLE never leaves the demonstration. PLANNING ESTIMATE never appears without its assumption.

LAYER 4

ONBOARDING — the execution contract

Conditions, not disqualifiers
REGISTER→ SURFACE→ COMPLY→ FLAG RISK→ COST→ EDUCATE

Then the standing rhythm:

GATE
enter at charter; baseline gate; authority gate; extend-or-close gate
LOG
every change beyond tolerance, with a named trade-off
SURFACE
exceptions on one dashboard, not in email
LAYER 5

PROHIBITIONS — automatic disqualifiers

Any violation blocks
NO NEW HOME
joins an existing function
NO NEW HIRE BY DEFAULT
redeploy first; new role has an exit
NO SAMPLE IN A REPORT
see Layer 3
NO PRIORITY WITHOUT A METRIC
a priority with no measure is not executable
NO METRIC WITHOUT AN OWNER
an unowned metric is not managed

VERDICT

  • ADMISSIBLEAll five layers pass. A decision record may be signed.
  • ADMISSIBLE WITH CONDITIONSNo blocking finding; every open gap is written down as a condition and accepted by the decider.
  • NOT YET ADMISSIBLEAt least one blocking finding. Fix the finding or stop the project; do not relabel the idea.

Reviewer: name · role · date

RULE: A project is admissible only when it can be specified, measured, resourced, linked to a named priority, and timeboxed — and when its review and stop rules are agreed before it starts.
